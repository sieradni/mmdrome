- *[2026-08-05]* **Metadata rating/love reads + album/artist filter semantics**:
  - **Rating quantization on read** (`metadataReader.ts::extractMetadataFromBuffer`): raw `file.getRating()` returns a normalized 0..1 = **POPM byte / 255** (not a percentage). `Math.round(r * 100)` turned 0.949… (POPM 242, a 4.5★) into 95/100 → 5 full stars. Fix: `rating = popmToLocalRating(Math.round(r * 255))` — 242 → 90 (4.5★), 255 → 100, and other MusicBee POPM bytes land on the 10-step grid. IMPORTANT gotcha: the WRITE map (`ratingToMp3Popm`) and READ map (`popmToLocalRating`) in `tagWriter.ts` are **asymmetric** (write is MusicBee-calibrated and user-verified: writes 204 for 90% but read maps 204 → 80). Do NOT "align" the write map to the read map — it would break MusicBee interop. Round-trip drift exists by design; the read map wins on rescan (re-sync will normalize values to the read map's grid).
  - **M4A loved flag (`LOVERATING`)**: MusicBee writes the loved flag into M4A/iTunes-style freeform atoms as key `LOVERATING` (no space), but ID3/TXXX uses `LOVE RATING`. `extractMetadataFromBuffer` now finds the loved key by `Object.keys(props).find(k => k.replace(/\s+/g,'').toUpperCase() === 'LOVERATING')` — covers both variants. The old hard-coded `props['LOVE RATING']` lookup silently missed MusicBee-tagged M4A files (reported "loved: No").
  - **Filter semantics (`libraryFilters.ts`)**: album/artist rating filtering is now **any-track** — a group passes when at least one of its tracks' ratings is in `[minRating, maxRating]` (implemented in `applyFilterSort` via a new `ratingOf` param + group `tracks`), instead of the old avg-based check that unrated (0) tracks dragged down. `makeGroupAggregates.avgRating` now averages **only rated tracks** (rating > 0) so sorting by rating isn't skewed by unrated songs. Callers pass `ratingOf` (AlbumsView/ArtistsView line: `applyFilterSort(albumGroups, $libraryFilters, getRating)`). Navidrome search `NavidromeSong` has no rating field, so no cross-source guard needed. SongsView was already per-track (filtered directly), unaffected.

  1. **The scan's `failed` counter only counts file-read errors** (`processItem`'s catch around `readFileMetadata`); rows that simply don't score a confident match are folded into `scannedCount`. `MetadataScanProgress` (appState.ts:44) has no no-match field — the result line cannot report them, so "11 failed" is the only nonzero signal while 111 rows silently sit inside "scanned".

  - **MD5 extracted** from navidromeApi into `src/lib/md5.ts` — it was already UTF-8-correct via TextEncoder (CJK titles hash correctly; pinned).
  - **Durable queue**: Dexie v6 table `pendingScrobbles`, unique compound index `&[kind+artist+track+timestamp]` makes duplicate enqueues DB-enforced no-ops. Flush engine processes one kind per cycle (each destination has its own call shape), backs off 30 s→2^n capped 8 min, rate limits (LFM 29 / LB 429) back off 15 min flat, poison rows drop after 8 attempts, time-sensitive kinds (`lfm-scrobble`, `lb-listen`) expire after 13 days (Last.fm rejects listens older than ~14 days). Loves never expire by age — they're idempotent writes worth retrying indefinitely until the attempt cap.
  - **Fan-out shape**: `scrobbleManager.evaluate` builds ONE `ListenEvent` and hands it to injectable destinations; each DEFAULT leg re-checks its OWN gates at fire time (toggle/session/token), so the manager stays gate-free beyond A9 accrual. Navidrome leg keeps its drop-on-fail policy (server bumps play counts itself); the asymmetry vs durable direct legs is deliberate (A11).
  - **Hearts are outward-only**: `commitFeedback` diffs the loved flag and enqueues `lfm-love/unlove` (+ LB feedback via `/1/metadata/lookup` → MBID → `/1/feedback/submit-log`; no-match skips gracefully with a surfaced counter). No reverse import — `user.getlovedtracks` has no love timestamps, so bidirectional merge has no basis; user decision 2026-08-25.
